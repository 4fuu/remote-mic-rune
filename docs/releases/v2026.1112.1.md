# Remote Mic Rune 2026.1112.1

This revision fixes the voice bridge never getting past "initializing"
on real hardware, which looked like an endless reconnect loop.

### Highlights

- **Root cause: a stale Windows GATT cache.** The bridge subscribed
  through cached service handles. After the remote reboots, Windows
  keeps serving the outdated attribute table and CCCD state: every
  subscribe reports success and writes are acknowledged, but the remote
  never actually enables notifications, so the ATVV handshake timed out
  on every cycle and the bridge retried forever. Discovery now always
  runs over the air (`BluetoothCacheMode::Uncached`), which also keeps
  the system cache fresh. Before this fix, removing and re-pairing the
  remote would temporarily paper over the problem by rebuilding the
  cache.
- **Second fix: the audio stack was silently poisoning the session
  thread.** cpal's WASAPI host initializes its calling thread as STA;
  the runtime loop never pumps messages, so WinRT could never deliver
  async-completion callbacks on that thread, and any over-the-air GATT
  operation would hang until its timeout. The voice runtime thread now
  claims MTA before anything else (cpal tolerates it).
- **Verified on a real RC003**: the bridge reaches Ready in about two
  seconds and stays connected with battery notifications flowing,
  where 2026.1112.0 timed out on every attempt.

### Install

- **`remote-mic-rune-2026.1112.1-x86_64-pc-windows-msvc-setup.exe`** —
  per-machine install under `Program Files\Remote Mic Rune`; upgrades
  in place over 2026.1112.0 (the installer stops a running helper task
  before upgrading).
- **`remote-mic-rune-2026.1112.1-x86_64-pc-windows-msvc.zip`** —
  portable copy. Keep `rc_agent.dll` next to `rc-helper.exe`.

After upgrading, reopen **Capture → Voice bridge** and enable it; no
re-pairing of the remote is needed.

Binaries are unsigned, so SmartScreen may warn on first launch.
